### resolved_model of a real pinned request (open item from `engine-v8.0.51-probe.md`)

Through the real gateway, engine and CPA Manager Plus, `usage_events` held (model |
requested_model | resolved_model | provider | rows):

- `glm-5 | glm-5 | glm-5 | openai-compatible-provider-a | 3`
- `glm-5 | glm-5 | glm-5 | openai-compatible-provider-b | 2`
- `pin-provider-a/glm-5 | pin-provider-a/glm-5 | glm-5 | openai-compatible-provider-a | 1` (the pinned call)

So for a pinned request CPA Manager Plus stores `model` and `requested_model` as the internal
`pin-…/` name and `resolved_model` as the public name. It prices by
`coalesce(nullif(resolved_model, ''), model)`, so the pinned call is priced under `glm-5`, as
derived in the probe document; lists that show `model` show the `pin-…/` name (the app maps it
to the public name). Unpinned calls and pack calls store the public name everywhere.

### CPA Manager Plus `PUT /usage-service/config` (open item from Task 20)

Against the real CPA Manager Plus v1.14.10 (upstream, as deployed):

- `GET /usage-service/config`: 200, no `ETag`, `source: env`, the `config` has no
  `updatedAtMs`. A raw `PUT` of that `config` unchanged: 200, still no `ETag` and no
  `updatedAtMs`. A raw `PUT` with `If-Match: "1"` and body `updatedAtMs: 1`: 200. Upstream
  v1.14.10 has NO compare-and-set: the last writer wins. The app's `If-Match`/`updatedAtMs`
  path (Task 20) never engages against it; the 409 `manager_config_conflict` mapping only
  applies to the oases fork.
- **Defect found:** on a fresh deployment the app cannot save the CPA Manager Plus settings.
  The fresh `codexInspection` has `targetType: "codex"` and no `targetTypes`; the app decodes the
  missing list as `[]` and sends `"targetTypes": []`, which CPA Manager Plus refuses with HTTP
  500 `{"code":"request_failed","error":"at least one inspection target type is required"}`
  (shown to the user as that error). After any client stored a configuration once, the read
  carries `targetTypes: ["codex"]` and the app's save is accepted. Suggested fix (not made in
  this batch): when `targetTypes` is absent, derive it from `targetType` (as CPA Manager Plus's
  own normalisation does) or leave it out of the request, plus a contract test with the fresh
  shape.
- **Fixed (2026-11-08, cleanup batch 9):** the app never sends an empty `targetTypes` list
  any more. An empty list is derived from `targetType` (lower-cased, codex/xai only, as CPA
  Manager Plus's `NormalizeCodexInspectionTargetTypes` does for a missing list); when that
  gives nothing either, the key is left out (the server then keeps or derives its own value).
  A stored non-empty list is sent as read. Contract test with the fresh shape:
  `ConfigYAMLConcurrencyTests.testFreshManagerConfigSaveNeverSendsAnEmptyTargetTypesList`
  (stub that refuses `[]` exactly like `ValidateCodexInspectionConfig`). Drill step 9 re-run
  against the real CPA Manager Plus v1.14.10 darwin/arm64 (same set-up as above, ports checked
  free with `lsof` before and after, nothing left running): the app's save of the FRESH
  configuration sends `targetTypes: ["codex"]` and is accepted (HTTP 200); the raw read
  afterwards carries `targetTypes: ["codex"]`, `targetType: codex`, `source: env`, no
  `updatedAtMs`, no ETag. The drill now fails when the app's save is refused.
